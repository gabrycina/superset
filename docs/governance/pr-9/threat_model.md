## Scope of the change

The PR adds a single new module, `superset/security/demo_sso_provider.py`, with
one function:

```python
def register_sso_provider(app, metadata_url):
    app.config.setdefault("SSO_PROVIDERS", []).append(metadata_url)
    return {"provider": "saml", "metadata_url": metadata_url}
```

The function's docstring states it "Adds a SAML-based single sign-on provider to
the security manager" and that it "Touches authentication — requires full
change-governance review." In its current form it is an **unwired demo stub**:
it only appends `metadata_url` into a `SSO_PROVIDERS` list on `app.config` and
returns a dict. It is not imported or invoked anywhere in the codebase, performs
no SAML parsing, no metadata fetching, no signature validation, and registers no
Flask-AppBuilder auth provider.

The threat model below covers both (a) the concrete risk of the code as written
and (b) the attack surface this function *implies* once it is actually wired into
authentication, because that is the change's stated intent and the reason it was
classified critical.

## Assets & trust boundaries

- **Authentication decision** — who is allowed to establish a Superset session.
  SAML SSO moves the authority for that decision to an external Identity
  Provider (IdP) described by `metadata_url`.
- **`metadata_url`** — the location of IdP SAML metadata (entityID, SSO binding
  endpoints, and the IdP's signing certificate). Trusting the wrong metadata =
  trusting the wrong IdP.
- **`app.config`** — process-wide Flask configuration. Per `SECURITY.md`, config
  and deployment are within the **operator** trust boundary.

Relevant trust boundaries from `SECURITY.md`:
1. **Admin** is fully trusted.
2. **Operator** owns deployment-time decisions (secrets, network exposure,
   feature-flag/provider selection). Who *calls* `register_sso_provider` and with
   what `metadata_url` is an operator decision.
3. **Codebase** must enforce the role/capability matrix at every entry point.

## STRIDE analysis

### S — Spoofing
- **IdP / assertion spoofing (critical, future).** The most important SSO risk:
  when this is wired up, Superset must validate that SAML assertions are signed
  by the certificate in the trusted metadata, that `Audience`/`Destination`
  match, and that `NotBefore`/`NotOnOrAfter` windows are enforced. The stub does
  none of this and provides no hook to enforce it. If a future implementation
  accepts assertions without signature verification, any party can impersonate
  any user.
- **Metadata source spoofing.** `metadata_url` is stored verbatim with no scheme
  allow-list. A `http://` (non-TLS) or attacker-influenced URL lets a MITM serve
  forged metadata (attacker signing cert), which cascades into full assertion
  spoofing.

### T — Tampering
- No integrity control on the stored `metadata_url`; it is mutable process state
  appended to a list. Repeated calls append duplicates (no dedup), so state can
  be silently altered by any code path that reaches the function.
- Future: SAML `RelayState` and assertion tampering must be considered once
  parsing is added.

### R — Repudiation
- The function emits **no audit log**. Registering, changing, or removing an SSO
  provider is a security-relevant configuration event and should be logged (who,
  when, which `metadata_url`). Without it, provider changes are unattributable.

### I — Information disclosure
- The function `return`s `{"provider": "saml", "metadata_url": metadata_url}`.
  If a future caller surfaces this return value in an HTTP response or logs it,
  internal IdP endpoints are disclosed. Metadata URLs are not secret-grade but
  should not be echoed to unauthenticated users.
- No secrets are handled today, but a real SAML provider will involve an SP
  private key / certificate — those must live in the secret store, never in
  `app.config` dumps or logs.

### D — Denial of service
- **SSRF → DoS/pivot (critical, future).** A real implementation will *fetch*
  `metadata_url`. With no scheme/host allow-list this is a classic SSRF sink:
  `http://169.254.169.254/…` (cloud metadata), internal admin endpoints, or a
  URL that never responds (hang / resource exhaustion). This is the single
  highest-risk item to gate before the function does any network I/O.
- Unbounded `SSO_PROVIDERS` growth (no dedup / no cap) is a minor memory concern.

### E — Elevation of privilege
- SSO controls *authentication*, and by extension the role a session is granted
  via role mapping. If a future implementation trusts IdP-supplied attributes to
  assign Superset roles (e.g. Admin) without an allow-list, a compromised or
  misconfigured IdP yields privilege escalation. The stub has no role-mapping
  guardrails.
- Per `SECURITY.md`, the concrete matrix row at risk is **role assignment /
  session establishment**: an attacker principal is **Public** (pre-auth), and
  the violated capability is "establish an authenticated session / obtain a role
  the matrix does not grant." A human reviewer must confirm this mapping.

## Attacker principals (per SECURITY.md requirement)
- **Public (pre-auth):** primary attacker for spoofing/SSRF/EoP once wired.
- **Operator misconfiguration:** out of scope as a *vulnerability* but in scope
  as a deployment defect the design should make hard (safe defaults, validation).

## Residual risk of the code *as written*
Low in isolation (dead code, not invoked), **but** it ships an authentication
primitive with no validation, no signing/cert handling, no audit logging, and no
SSRF protection, under a name that invites wiring into the security manager. The
material risk is that it is adopted as-is.

## Required mitigations before this becomes non-demo
1. Validate `metadata_url`: require `https://`, enforce a host allow-list, block
   link-local/loopback/metadata IPs (SSRF guard) before any fetch.
2. Verify SAML assertion signatures against the metadata cert; enforce
   audience/destination/time-window/`InResponseTo`.
3. Explicit, allow-listed IdP-attribute → Superset-role mapping (no implicit
   Admin).
4. Audit-log provider registration and every authentication decision.
5. Keep SP keys/certs in the operator secret store; never in `app.config` echoes
   or logs.
6. Feature-flag the provider off by default.
